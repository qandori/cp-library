# 多項式逆元の必要な列だけを計算する

## 変更

`polynomial_inv_mod` が必要とする Bézout 係数は一つだけなので、全体の変換行列の第1列だけを更新する。公開 API、通常の GCD、拡張 GCD、Half-GCD の基底処理は変更しない。係数型の変換、零・定数・非可逆入力の扱いも維持する。

各段階の多項式を `A = x a + y m`, `B = u a + v m` と書くと、逆元に必要なのは `x, u` である。Euclid の1段は `(x,u) -> (u,x-q u)`。Half-GCD の完全な行列 `P` が局所的な多項式対へ作用するとき、蓄積する列も `P (x,u)^T` にする。第2列を作らなくても第1列は完全な行列積と一致する。最後に GCD が非零定数なら第1成分をその定数で割り、法で剰余を取る。局所的な Half-GCD 行列は完全なままであり、部分的な行列を多項式対へ作用させることはない。

内部の `multiply_column` は大きい積で前方 NTT を8本から6本、逆 NTT を4本から2本に減らす。`step_column` は係数多項式の積を二つから一つにする。元の `multiply` / `step` のシグネチャと処理は残す。計算量のオーダーは変わらない。新しい命令セット依存や乱数依存は追加しない。

## 参考

[既存の多項式 GCD 調査](polynomial_gcd.md)で確認した [Library Checker 409589](https://judge.yosupo.jp/submission/409589) は、Half-GCD の変換キャッシュと必要な成分だけの計算を使う。[maspy の実装](https://github.com/maspypy/library/blob/main/poly/poly_gcd.hpp)の完全な行列による変換も参照した。今回の比較対象は既存の本ライブラリであり、参考提出を今回の測定環境で再測定したものではない。

## 比較方法

2026-10-17、Linux x86_64、Intel Xeon Platinum 8573C、GCC 14.2.0。CPU 0 に固定した。これは AtCoder 実機の測定ではない。

- baseline: commit `6af78c247f5c9beba109116966f3a3d4e9dc5104` の完全な拡張 GCD を使う逆元。
- column: 今回の第1列だけの実装。採用対象。
- fused: column に、基底 Euclid の剰余・変換更新を同じ領域で計算する実験を追加したもの。今回の本体には入れない。比較コードには残す。
- generic: `-std=c++23 -O2 -DNDEBUG -Wall -Wextra`。
- native: generic に `-march=native -ftrivial-auto-var-init=zero` を追加。

変更した型・関数名を実装別に分離し、三つを同じ実行ファイルへ入れる。変更していない FPS / NTT は共有する。各条件で1回ずつウォームアップする。6試行では三つの順序を回転・反転し、各実装が各位置に2回ずつ現れる。各実装の実測した `CLOCK_PROCESS_CPUTIME_ID` の合計が0.15秒以上になるまで反復する。小入力では64回をまとめて計測する。

入力生成と結果の全係数を走査するチェックサム計算は時間外。関数呼び出し、入力コピー、内部の変換・確保、結果の受け渡しは時間内。全試行のチェックサムを照合した。18条件・2設定・6試行・3実装、計648標本を保存した。外れ値や不利な条件を削除していない。

表の時間は各実装の中央値、単位は ms。速度比は同じ試行の `baseline / candidate` を先に求めた中央値であり、時間中央値同士の比ではない。角括弧は6個のペア比の最小・最大。`n` は最初に作る多項式の係数数で、共通因子の場合は両入力にさらに `n/3` 係数の因子を掛ける。通常の dense は係数数 `n, n-1`、asymmetric は後者を `n/8` にする。sparse は `x^(n-1)-1` と `x^(n/2-1)-1`、equal は同一、constant は後者を7にする。逆元では後者を前者を法として反転する。`n=1` は定数を法とする空の結果の経路。

## 判断と制約

第1列だけの実装では、dense な逆元の `n=32..65537` のペア速度比中央値が generic で1.228〜1.561倍、native で1.271〜1.669倍だった。generic の `n=50000,65537` は全6ペアで改善し、中央値は1.233倍・1.291倍だった。generic の dense 8サイズ中7サイズは全6ペアで改善した。native でも `n=128,1024` と asymmetric `n=4096` は全6ペアで改善した。これらを今回の主な判断材料とし、ばらつきの大きい native `n=50000` の1.669倍を代表的な改善率にはしない。

全入力での無劣化は示していない。column の不利なペア中央値として、generic の定数法 `n=1` は0.947倍、equal は0.953倍、通常の GCD `n=4096` は0.965倍、native の拡張 GCD `n=50000` は0.922倍を残した。定数法の個別時間中央値は generic で約61.9nsから65.4ns、native の拡張 GCD は約247.3msから269.4msだった。generic の sparse `n=50000` はペア比中央値0.989倍だが、個別時間中央値は4.897msから5.215msで、中央値同士の比は0.939倍だった。二つの集計方法を同一視しない。通常の GCD・拡張 GCD の処理は変えていないが、測定された不利な結果を除外しない。

ばらつきも大きい。generic の逆元 `n=256` には column が0.072倍のペアがあり、native の逆元 `n=50000` の column は0.169〜5.873倍だった。原因は特定していない。中央値を安定した最低保証や実機の改善率として扱わず、generic と native の絶対時間から設定間の優劣も断定しない。

fused は多くの条件でさらに速い一方、基底処理まで変更範囲が広がり、native の constant では0.941倍だった。今回は変更範囲の狭い column を採用候補とし、fused は別の検討に残す。別途試した fraction-free 基底処理は一貫した改善が得られず、この本体・最終比較には含めない。測定した三実装の構成を保持するため、fused の比較用生成コードを削除しない。

## 正しさと互換性

小入力の素朴な GCD、Bézout 恒等式、逆元の積、零・定数・末尾零・同一入力・整除・共通因子・非2冪・異なる係数型を確認した。第1列の積・Euclid 更新を完全な行列の同じ列と比較するテストを追加した。

独立した検証では、column と fused の双方について GCC O2 と ASan/UBSan の素朴解比較が成功した。各実装の検証対象は284ケースと750個の行列変換で、恒久単体テストも成功した。Mac とマージ対象最新版の CI は別途確認が必要であり、このローカル結果だけでマージ可能とはしない。

## 再現

ベンチマークスクリプトは Linux 用 (`sched_setaffinity`, process CPU clock) であり、ライブラリ本体の Mac 対応とは分ける。`lscpu` が利用できない場合は失敗情報と `/proc/cpuinfo`・利用可能 affinity を記録する。

```sh
python3 test/benchmark/polynomial_inv_mod.py --output /tmp/polynomial-inverse-generic --trials 6 --cpu 0
python3 test/benchmark/polynomial_inv_mod.py --output /tmp/polynomial-inverse-native --trials 6 --cpu 0 --native
```

生の標本、入出力チェックサム、コンパイラ・CPU・フラグ・ソース SHA-256 は実行時の出力先に保存し、リポジトリには追加しない。初回計測前の補助スクリプト修正は `lscpu` 失敗の記録、CPU affinity マクロの文法、既存 NTT の `NDEBUG` 時の未使用変数警告をエラーにしない設定だけであり、計測後の実装・計測コード変更はない。

# FPS 対数と最速提出との差

2026-10-18（Asia/Tokyo）、`3dd3db7c749ba3c00d432fc82b085146f86c4b0e` を調査した。参照は [409452](https://judge.yosupo.jp/submission/409452)、ソース SHA-256 は `86ef3c3b4a4707ef5e7515e5229b2564f2a5f46bd830bb6cbe64b506a95675b6`。今回の変更は診断と測定資料で、ライブラリ本体は変更していない。

## 結論

前回移植したのは、最大 4 ブロックでの対数微分と Toeplitz 積という計算手順である。最速版の NTT バックエンド・入出力・メモリ配置全体は再現していない。「同じ手法だから同じ速度になる」という説明では不十分だった。

同じ最速コードを同じ条件で実行すると約 13 ms を再現できる。また、公開 API と同じ `const fps&` から `fps` を返すラッパーの中でも、最速版の計算部分そのものは約 8.75 ms を維持する。公開 API が高速な計算カーネルの導入を妨げている証拠はない。

差には計算カーネルに加え、入出力と、通常の vector 配列を入力・結果に追加で持つ費用が含まれる。内部カーネルだけの移植でプログラム全体も 13 ms になる、とも言えない。

## 条件

Linux x86_64、AMD EPYC 9V74、GCC 14.2.0、CPU 2 に固定。フラグは `-std=c++23 -O2 -DEVAL -DONLINE_JUDGE -ftrivial-auto-var-init=zero -march=haswell`。assert 有効、既存ヘッダーの局所的な O3 指定も有効。

公式 `log_of_formal_power_series/in/max_random_00.in`、N = 500,000 を通常ファイルから読み、通常ファイルへ出力する。予備実行 1 回と 21 試行。プロセス全体の比較は seed 20261018 で順序をシャッフルする。全出力を公式 checker で照合した。checker は計時外で、測定中にコンパイルや別の検証を並行実行していない。

以下はローカルでの中央値、単位 ms。掲載時間や異なる測定セッションとの差を混ぜない。各行の生の値・ハッシュ・生成スクリプト・公式問題のコミットは [記録](results/fps_log_gap.json) に保存した。

## プロセス全体

最初の比較行列（記録の `measurements.whole`）。

| 版 | ms |
| --- | ---: |
| 現在版 | 22.293 |
| 最速提出のソースそのまま | 13.064 |
| 最速版を通常の main から実行 | 13.347 |
| 最速版の計算 + 現在の scalar 入出力、係数は通常剰余 | 17.275 |
| 最速版の計算を単純な fps API ラッパーで呼ぶ + 現在の入出力 | 21.821 |
| 現在版の計算 + 最速版の入出力、境界で fps に変換 | 19.715 |

`reference_normal` は ELF preinit と `_exit` だけを外したもの。`reference_common_io` は最速版の Arena に通常剰余を直接読み書きするので、fps API ラッパーとは違う。これらの差を、そのまま API の不可避な費用とは扱わない。

最速版の `namespace ntt` と既存ライブラリのグローバル関数 `ntt` が衝突するため、同時に include する比較版では参照側の識別子を `gap_ntt` に変更した。計算内容は変えていない。元ソースそのままと通常 main の版にはこの変更もない。

## 処理別の内訳

コピーしたソースだけに `steady_clock` の計測を追加した別実験（`measurements.phases`）。本体には計測を入れていない。計測によるコンパイル結果の変化を含むため、この表と上の未計測版の値を引き算して厳密な加算分解にはしない。

| 処理 | 現在版 | 最速版 |
| --- | ---: | ---: |
| 入力の取得と係数読み込み | 4.192 | 1.070 |
| 最速版の Arena・変換表の準備（計算前） | — | 0.197 |
| log 呼び出し | 12.583 | 8.800 |
| うち初期逆数 `1/f mod x^k` | 2.429 | 1.666 |
| うち結果・作業領域・変換表などの準備 | 1.407 | — |
| うち逆数と入力窓の順変換 | 1.662 | 1.210 |
| うち残差の積・逆変換・微分からの減算 | 2.329 | 2.016 |
| うち残差と逆数の積から各商ブロックを復元 | 3.285 | 2.755 |
| うち商ブロックの変換キャッシュ | 0.962 | 0.746 |
| うち積分 | 0.327 | 0.373 |
| 出力の変換・書き出し・flush | 3.671 | 1.393 |

計算呼び出しには約 3.78 ms、入出力には合計約 5.40 ms の差がある。初期逆数も含む複数の変換で差があり、積分はこの測定で現在版のほうが短い。積分だけをさらに調整する優先度は低い。

## 単純な API ラッパーが遅くなる理由

ラッパーは入力を変更せず、公開型のまま結果を返す。内部に最速版と同じ Transform・Arena・log を置き、境界で `a[i].val()` と `Mint::raw()` を使う。このラッパーは最大入力の診断用で、空入力や任意の出力次数など API の全条件を実装した製品版ではない。

別の比較行列（`measurements.api`）では、このラッパーは 22.260 ms。ラッパー関数に O3 を指定すると 20.793 ms だった。逆アセンブルでも、単純版の変換ループに係数ごとの `Mint::val` / `Mint::raw` の call があり、O3 版ではその call が消えることを確認した。O2 の呼び出し側とヘッダー内の局所 O3 指定の境界も考える必要がある。

O3 を main 全体に指定するだけの版は 22.201 ms だった。最適化指定を広げれば必ず速くなるわけではない。

境界の専用 O3 関数と最速版の入出力を使う比較（`measurements.boundary`）。

| 版 | ms |
| --- | ---: |
| 現在版 | 22.235 |
| 最速提出そのまま | 13.075 |
| 最速版、通常 main | 13.253 |
| 最速計算 + O3 API ラッパー + 最速入出力、入出力境界は単純ループ | 18.113 |
| 上記の入出力境界も専用 O3 関数にする | 17.464 |

最後の版の処理別計測（`measurements.fast_api_phases`）では、入力 2.666、API ラッパー 10.677、出力 1.936 ms。ラッパー内の内訳は次のとおり。

| 処理 | ms |
| --- | ---: |
| Arena と変換表 | 0.181 |
| fps 入力から通常剰余への変換 | 0.329 |
| 最速版の log 計算 | 8.755 |
| 結果 fps の確保と初期化 | 1.184 |
| 通常剰余から結果 fps への変換 | 0.196 |

さらに入力側にも、fps 配列の確保・初期化 1.133 ms、通常剰余から fps への変換 0.438 ms がある。これらは元の最速プログラムにはない。通常ページの確保・初期化・初回アクセスを分離して測ってはいないので、全額をゼロ埋めだけの費用とは断定しない。

したがって「最速関数を呼ぶだけ」のラッパーでも計算は同じ速度で動くが、元のインプレースな通常剰余配列と同じメモリ経路にはならない。入力を二重に持つ比較用ラッパーのコストを、そのまま API の下限と考えるのも誤りである。

## まだ取り込めていない実装

| 箇所 | 最速版 | 現在版 |
| --- | --- | --- |
| log 用バックエンド全体 | 専用 Transform と assembly カーネル | 共通 NTT と LogTransform の組み合わせ |
| 葉の処理 | 最終 butterfly・正規化・環積・逆 butterfly を融合 | 順変換・正規化走査・葉の積・逆変換を分離 |
| 積の準備 | Window を二重化し次の群を先行準備 | 64 要素をスタックへコピーし、重みと積を別に準備 |
| 変換の走査 | 深さ優先で 2048 ワード以下をまとめて処理 | 各段で配列全体を走査 |
| 変換表 | root と Shoup quotient を 8 個ずつ隣接配置 | root・quotient・補助表を別 vector に保持 |
| 末尾の倍率と出力 | 最上段に倍率を融合し必要な半分だけ書く | 順変換後の別走査で倍率・正規化、逆変換は両半分 |
| 逆数の Newton 更新 | 同じ専用カーネルで積と半分の復元 | 共通 NTT 側の実装 |
| 作業領域 | 入出力・表・作業領域を一つの Arena に置く | 作業領域は THP 対応、入力・結果・表は別確保 |
| 入力 | AVX2 bulk parser | 一係数ずつの整数読み込み |
| 出力 | 16 値ずつ SIMD で固定幅に整形 | 一係数ずつの整数整形 |
| プロセス起動終了 | preinit で実行し `_exit` | 通常 main と通常の終了処理 |

ただし、違うというだけで各項目が主因とは言えない。最速版のコードから一つずつ外した比較は次の結果だった（最初の比較行列）。

| 最速版の変更 | ms |
| --- | ---: |
| 通常 main の基準版 | 13.347 |
| log と Newton 更新で両半分を復元 | 13.310 |
| 再帰タイルの閾値を十分大きくし、全体を段ごとに処理 | 13.251 |
| cyclic_product の順変換を独立させる | 13.279 |
| Window の先行準備を外す | 13.670 |
| 葉の積だけを assembly から intrinsics に置換 | 13.537 |

最初の 3 候補は基準版のばらつきと重なり、個別の速度向上を示していない。先行準備と葉の assembly の差も小さく、これらだけで全体差を説明できない。特に「片半分を計算しない」「融合する」「再帰化する」の単独の追加を最優先とする根拠にはならない。変換表の配置と butterfly assembly を含むバックエンド全体の効果は、この実験では個別に切り離していない。

## 次の実装の優先順位

1. 現在と同じ API の内側で、最速版の Transform・初期逆数・対数微分を一組として移植する。今回のラッパーで計算速度を保てた構成を基準にし、別の NTT へ手法だけを載せ替える段階を終える。まず約 8.8 ms の計算時間を再現する。
2. FPS 入出力に bulk 経路を用意し、Montgomery 変換もまとめる。最速版の「通常剰余を読み、Montgomery にし、通常剰余へ戻す」比較用の二重配列を本実装へ持ち込まない。scalar の汎用入出力の契約は保つ。
3. 最大の変換表を初めに用意し、作業領域と結果の確保・初期化・コピーを減らす。最速版と異なる vector の費用を含めたプロセス全体で再測定する。
4. その構成で個別の assembly・融合・半分の復元を比較する。preinit / `_exit` の約 0.2–0.3 ms はライブラリへ持ち込む優先度が低い。

安全性の維持には、AVX2 実行時分岐と従来のフォールバック、入力を変更しないこと、入力長と出力次数が異なる場合、余分な入力 padding を要求しないことを引き続き守る。参照側の mmap 失敗処理・Window の末尾ロード・アラインメント・オブジェクトの生存期間も移植時に確認する。これらは移植で扱う条件であり、API 変更を要するという結論ではない。

参照ソースと公式入力の用意は [既存の手順](fps_speed.md#再現) に従う。各 suite はすべてのビルドを済ませてから計時する。

```sh
python3 test/benchmark/fps_log_gap.py --reference-source /tmp/fps-reference/log_of_formal_power_series/409452.cpp --official-root /tmp/library-checker-problems --work-dir /tmp/fps-gap-repro --output /tmp/fps-gap-repro.json --suite main
python3 test/benchmark/fps_log_gap.py --reference-source /tmp/fps-reference/log_of_formal_power_series/409452.cpp --official-root /tmp/library-checker-problems --work-dir /tmp/fps-gap-repro-api --output /tmp/fps-gap-repro-api.json --suite api
python3 test/benchmark/fps_log_gap.py --reference-source /tmp/fps-reference/log_of_formal_power_series/409452.cpp --official-root /tmp/library-checker-problems --work-dir /tmp/fps-gap-repro-boundary --output /tmp/fps-gap-repro-boundary.json --suite boundary
```

処理別計測は、記録 JSON の `generation_scripts` に実際に実行したスクリプトも保存している。`experiment.py`、`profile.py`、`api.py`、`api_profile.py`、`boundary.py`、`fast_profile.py` の順で実行すれば、生成した比較ソースと処理別計測を再構築できる。記録内の `/workspace/cp-library`、`/tmp/fps-gap`、参照ソース、公式問題のパスは実行環境に合わせる。再現用生成器が作る全 23 比較ソースの SHA-256 は、測定したソースと一致することを確認した。合計 616 回の実行（予備実行を含む）の出力を checker で照合した。ライブラリ本体を変更していないので、既に成功した単体テストと他問題の検証は繰り返していない。結果の速さは対象 CPU・ジャッジで改めて確認する必要がある。

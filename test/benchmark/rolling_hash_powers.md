# Rolling Hash の累乗キャッシュ構築

2026-10-17、Linux x86_64 / Intel Xeon Platinum 8573C / GCC 14.2.0。既存の `rolling_hash.md` は macOS で累乗キャッシュを構築済みとして測定した別の比較です。本資料は初回の累乗生成と追加確保を対象にし、Mac の速度は評価していません。

## 変更

`ensure_powers` の追加要素が 16 個未満なら従来の逐次計算を維持し、それ以上なら `b^4` を使う 4 本の独立な漸化式を交互に進めます。最初の 3 要素を逐次計算してから 4 要素ずつ処理し、残りも同じ式で処理します。公開 API、基数、法、ハッシュ値、共有キャッシュの仕様は変えません。

比較元は main `0841637ff8d5f59b4021775e812f66abef82cbdd` のヘッダーです。基準版 `815bc8bf` とも同一でした。

- 比較元 SHA-256: `ca48dbc8344472d686ce156eef7d1314a387b9c167c595cfa55761d5d4e441f5`
- 候補 SHA-256: `c808787cb1c74e2f28eeb4604427a0329d420d71f441ed684a0b24c83f2592d8`
- `components/splitmix64.hpp` SHA-256: `84e473d5ce9fcc1bc86e1a7c11c09aa032d9adc40b8e69a7114c137dbd1ba239`

## 測定方法

両版とも `-std=c++23 -O2 -DNDEBUG -Wall -Wextra -Werror`、native だけ `-march=native` を追加しました。同じ許可済み論理 CPU 0 に固定し、各ケースの共通反復数は両版が 0.50 CPU 秒以上になるまで増やしました。その後の 10 ペアは AB/BA を交互に実行しています。採用する実測バッチ時間の下限は事前に 0.10 秒とし、実際の最小値は 0.443625 秒でした。200 ペアをすべて保持し、除外や符号に応じた追加測定はしていません。入力生成と検証は計測外です。

- cold reserve: 累乗キャッシュを `{1}` に戻して `reserve(n)`。
- cold build: 累乗キャッシュを `{1}` に戻して文字列のハッシュを構築。キャッシュのリセット・解放、累乗の確保と生成、prefix の確保・生成・破棄を双方に含めます。繰り返し測るためのリセットを含む「新しい累乗キャッシュでの構築」であり、プロセス起動時間や OS キャッシュを消去した測定ではありません。
- warm build: 両版とも累乗キャッシュを事前に構築してから文字列のハッシュを構築・破棄。
- reserve +7: キャッシュをリセットし、1 から 7 刻みで延長して最後に n まで確保。

計測専用コピーでは、include guard とクラス名を変更し、依存ヘッダーを絶対パスにし、共有キャッシュと prefix の検証のため private を public にしています。また両版の `base()` は、コマンドラインから設定した同一の実行時変数を static local の const 値へ読む形に置き換えました。基数は `12345678901234567`、文字列 seed は `71239` です。各 static local の初期化ガードは残し、初回の基数初期化自体は検証時に済ませています。基数を関数内のコンパイル時定数にして乗算が特殊化される比較は避けました。これら以外に、提案する `ensure_powers` の差以外の処理変更はありません。

10K / 1M / 8M の cold build は generic で 1.324 / 1.400 / 1.210 倍、native で 1.333 / 1.349 / 1.165 倍でした。一方で、すべての入力・処理が速くなる結果ではありません。

- native の cold build、n=16 はペア中央値 0.945286 倍です。個別の時間中央値は旧版 0.152653 µs、候補 0.150974 µs、全ペアの範囲は 0.770415–2.858248 倍でした。この不利なペア中央値を除外していません。
- native の warm build、n=64 はペア中央値 0.967233 倍です。個別の時間中央値は旧版 0.347944 µs、候補 0.356022 µs、全ペアの範囲は 0.488916–4.696153 倍でした。事前に置いた「warm/incremental の 3% を超える低下は再検討」という screen 基準には、このケースは未達です。これはユーザーの指定条件ではなく、本実験の評価基準です。
- native の cold build、n=64 には 0.236087 倍のペアがあり、最大 wall/CPU 比は 1.518333 でした。大きなばらつきは測定上の限界であり、不利な値を除外したり、無条件にノイズと断定したりする理由にはしていません。
- 今回の generic/native バイナリでは旧版の `ensure_powers` はインライン化され、候補は別関数として warm build からも呼ばれていました。小さな warm 処理の呼び出しコストが増える可能性はありますが、この差の寄与は個別に定量化していません。

したがって、大きな新規キャッシュ構築の改善を示す結果であり、「全ケースで低下なし」を満たした結果ではありません。小入力のトレードオフを含むドラフトとして評価し、この測定や CI の成功だけで無条件に採用する根拠にはしません。

## 正しさの確認

計測専用コピーは基数 256 / 257 / 12345678901234567 / mod−257 で検証しました。開始サイズと成長量の全組合せ 0..64、1/2/3/4/7/15/16/17/31/32/33/63/64/65 刻みの成長、長さ 0..257 のランダムバイト列の全区間を、128 bit の `%` を使う独立計算と照合しています。各モード実行直後の全累乗も比較し、最後の逐次成長で上書きされた後だけを比較することは避けています。

`test/unit/rolling_hash_powers.cpp` は本番のランダム基数と公開 API のまま、成長境界、既存キャッシュの再利用、全累乗、整数の境界値、部分文字列と連結を検証します。推移的な利用先を含む検証対象は既存の `rolling_hash`、`rolling_hash_monoid`、`hld`、`standalone` と AOJ/Library Checker の両 judge driver です。

ローカルでは GCC 14.2.0 による本番ヘッダーの standalone 検査と上記 5 unit の通常実行、ASan/UBSan 実行が成功しました。LSan はこの環境で未対応のため `ASAN_OPTIONS=detect_leaks=0`、UBSan は `halt_on_error=1` です。初回検証後に main が `7502f01521bcccc63569a160fe2cef0e41eac936`（FPS 分割）へ進んだため、再帰的 include の差分を確認しました。rolling_hash・powers・monoid・HLD・両 driver の依存は変更がなく、変わった standalone のみ新しい main 上で通常・ASan/UBSan を再実行して成功しています。

新しい verifier/planner のテストは 37 件中 36 件が成功、online-judge-verify-helper が未導入のため 1 件を skip しました。AOJ driver は独立な KMP による 208 ケース、LC driver は独立な Z Algorithm による 152 ケース（公式 example 入力 2 件を含む）と一致しました。これはローカルの driver 検証で、公式 judge の全データを実行した結果ではありません。Clang と Mac はローカルにないため未実行で、別途 CI での確認が必要です。計測は main 更新後も再実行していません。

## Library Checker の比較対象

関連する LC verifier は [Z Algorithm](https://judge.yosupo.jp/problem/zalgorithm) です。2026-10-17 の公式 API の AC / 時間昇順一覧では、次の先頭 3 提出がいずれも 0.006 秒でした。同率のため単独最速とは扱いません。

- [391971, firiexp](https://judge.yosupo.jp/submission/391971): SHA-256 `e8c49043a41774f58f11a5646067c5adb26f358d557df516757c8915de71aaca`
- [362494, IceKylin](https://judge.yosupo.jp/submission/362494): SHA-256 `34fb452e6758529f8bdfd9d9fd8a9e0496573fdf4efd5893b176126c1b9a4022`
- [362211, IceKylin](https://judge.yosupo.jp/submission/362211): SHA-256 `46ffe83bfe60b55198b75c5388052665cb63d449189f58b4da44daf4e46fa88e`

これらは直接の文字比較と線形時間の Z-box 法、独自の入出力を使い、rolling hash や累乗キャッシュを使っていません。関連問題の手法比較として調査しましたが、汎用 RollingHash API の置き換えや累乗生成の同条件ベンチマーク相手にはしていません。コードは転用しておらず、この環境で提出全体との速度比較もしていません。

## 再現

Linux / GCC 向けのスクリプトです。候補ヘッダーから計測専用コピーを生成し、正しさの検証後に 10 ケースずつ generic/native を測ります。CSV、環境情報、ハッシュと検証ログは指定した出力先へ保存します。

```sh
python3 test/benchmark/rolling_hash_powers.py --output /tmp/rolling-hash-powers --cpu 0
python3 test/benchmark/rolling_hash_powers_reference.py --output /tmp/rolling-hash-powers-reference
```

コピーの生成だけなら `--prepare-only` を指定します。`--cxx` と `--cpu` でコンパイラと許可済み CPU を指定できます。元の 200 ペアは一度の凍結した screen の結果であり、上の再現用スクリプト作成後に計測をやり直していません。

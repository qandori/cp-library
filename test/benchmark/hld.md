# HLD のベンチマーク

GitHub Actions の `hld benchmark` で Linux x86_64/GCC の比較と関連する公式問題の検証を実行できます。ローカルで再現する場合はリポジトリのルートで次を実行します。比較元 `fe21ba0` を含む Git 履歴が必要です。

```sh
python3 test/benchmark/hld_variants.py /tmp/hld-variants
g++ -std=c++23 -O2 -DNDEBUG -I . -I /tmp/hld-variants test/benchmark/hld.cpp -o /tmp/hld-bench
/tmp/hld-bench 500000 500000 5 > /tmp/hld.csv
```

引数は頂点数、問い合わせ数、試行数です。`-DNDEBUG` を外した測定も行っています。頂点ラベル・辺順をシャッフルし、根は `n / 3`、固定シードを使います。直線・星型・平衡二分木・ランダム木・長い幹を持つ木を比較します。`broom` は半数を直線にし、残りを既存頂点へランダムにつないだ木です。問い合わせには範囲外の距離と距離 0 も含めます。

各試行で実装の順序をシャッフルし、入力生成・正解計算・照合を計測から除外しています。問い合わせごとに結果を保存し、計測後に変更前と全件照合します。パス分解は頂点値の累積和から各区間の和を取り、頂点の並び方が変わっても結果を比較できるようにしています。非可換なパスの順序はユニットテストで確認します。各操作のループは別関数に分け、ほかの操作のコード量がインライン化に与える影響を抑えています。

参考にした AC 提出です。2026-10-16 に実行時間順の上位を確認しました。

- [Jump on Tree 403437](https://judge.yosupo.jp/submission/403437): 葉の削除と隣接頂点の XOR による構築、直線・星型の専用処理、問い合わせ情報の集約を参考にしました。
- [Jump on Tree 270103](https://judge.yosupo.jp/submission/270103): オフラインで祖先を求める方式です。オンラインで使える既存 API を保つため採用していません。
- [LCA 278239](https://judge.yosupo.jp/submission/278239)、[Vertex Add Path Sum 278241](https://judge.yosupo.jp/submission/278241): RMQ や Fenwick Tree を利用する、問題に特化した処理を確認しました。
- [Vertex Set Path Composite 319096](https://judge.yosupo.jp/submission/319096): 経路集約用の構造と HLD の組み合わせを確認しました。

比較した変更は次のとおりです。

| 名前 | 変更 |
|---|---|
| `baseline` | `fe21ba0` の HLD |
| `preorder` | 頂点の並び順で比較し、祖先探索の目標深さを固定 |
| `fused` | `preorder` に jump の探索と早期終了を統合 |
| `peel` | 葉の削除で親・部分木サイズ・重い子を求め、CSR の構築と走査を省略 |
| `peel_preorder` / `peel_fused` | 上記の組み合わせ |
| `peel_zero` | 距離 0 の jump を早期終了 |
| `packed` | 位置・連鎖先頭・連鎖の親・深さの差を頂点ごとに集約 |
| `shapes` / `packed_shapes` | 直線・星型での LCA・祖先・jump を定数時間で処理 |
| `current` | `packed_shapes` を基に、直線のパス分解も直接処理する現在の `graph/hld.hpp` |

問い合わせ用の配列は 1 頂点あたり 16 バイト増えます。50 万頂点で約 8 MB です。構築中の一時配列は CSR の約 12 バイト/頂点から約 8 バイト/頂点へ減ります。公開配列・辺を含む主要な配列の合計は約 40 バイト/頂点から約 56 バイト/頂点になります。計算量は構築・空間が $$O(n)$$、一般の問い合わせが $$O(\log n)$$ のままです。

これらは HLD 単体の比較で、入出力や Segtree を含む提出全体の時間、各 judge の実行時間とは区別してください。

## Linux/GCC での実測

2026-10-16 の [GitHub Actions run](https://github.com/qandori/cp-library/actions/runs/38843681932) です。変更前を含む 11 実装を同じジョブ内で比較しました。環境・全試行の CSV・公式テストログは artifact `hld-linux-gcc-benchmark` にあります。通常の verify も [成功しています](https://github.com/qandori/cp-library/actions/runs/38843681261)。

測定元は `fe21ba0`、測定した採用版は `eae11ea7b7791b14a75f6d67876445eedee58aa1` の `graph/hld.hpp` です。

Ubuntu 24.04 / INTEL(R) XEON(R) PLATINUM 8573C / `g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0`。5 試行の中央値、単位は ms です。

試行では、並び順による比較だけでは星型の LCA が遅くなり、情報集約だけでは直線の LCA が遅くなるケースがありました。直線・星型の判定と専用処理を組み合わせています。最初の採用候補で直線のパス分解にも退行があったため、最終版では連鎖の位置から直接区間を返します。

公式問題は Jump on Tree 21 件、Vertex Set Path Composite 20 件、Vertex Add Path Sum 19 件、Vertex Add Subtree Sum 16 件を GCC・Clang で確認しました。GCC・Clang の単体検証と ASan・UBSan も成功しています。非 0 の根、再構築、コピー、辺の向き、非可換な経路、`INT_MIN`・`INT_MAX` の距離も検証対象です。

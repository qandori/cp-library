# 桁数が偏った BigInt の乗算

## 変更

短い入力が 9～32 limb、長い入力が 257 limb 以上の場合に、既存の筆算を使います。1 limb は十進 18 桁です。短い入力が 8 limb 以下、両入力が 256 limb 以下、短い入力が 33 limb 以上の分岐は維持します。公開 API・符号処理・内部表現は変更しません。

基数を B = 10^18 とすると、係数に重なる積は最大 32 個です。繰り上がりは 32(B−1) 以下であり、積和と繰り上がりの合計は 32B(B−1) < 2^128 に収まります。既存の unsigned 128-bit 筆算を使用し、新しい SIMD 命令やプラットフォーム依存処理は追加しません。筆算の追加作業領域は結果配列で、変換用の一時配列を使いません。

## 参考

2026-10-17 に Library Checker の multiplication_of_big_integers の AC を確認しました。[提出 389886](https://judge.yosupo.jp/submission/389886) は記録上 25 ms で、基数 10^8、短い入力が 96 limb 未満の場合の筆算と、長さが偏った場合のブロック FFT・短い側の変換の再利用を使っています。この時間は入出力を含み、本ライブラリのローカル計測とは比較できません。

今回は FFT の実装は移植せず、基数 10^18 の既存の正確な整数筆算に切り替える範囲を限定しました。参考ソースの SHA256 は 79e6dce4b3c6afab1a1e7bd231bdaee37071d8a78e798071649ec1a0e1954756 です。

## 再現方法

Linux x86_64 で、リポジトリのルートから実行します。

```sh
python3 test/benchmark/bigint_unbalanced.py --output /tmp/bigint-unbalanced --trials 7
```

既定の比較元は 6af78c247f5c9beba109116966f3a3d4e9dc5104 です。異なる比較元は `--base`、利用可能な CPU は `--cpu` で指定します。依存ヘッダーが比較元と同じことを確認し、旧・新の BigInt を別名で同一バイナリに組み込みます。コンパイラは `--cxx` で指定できます。

固定シードの入力 4 組を構築し、全積の十進表現の一致を計測前に確認します。乗算と結果の uint64_t 変換によるチェックサム消費を計測し、入力構築と十進文字列への変換は含めません。旧・新それぞれの反復数を校正し、各測定が実測 CPU 時間で 0.20 秒以上になるまで実行します。測定順は寸法と試行番号に基づいて交互にします。7 組の旧・新測定の時間比の中央値を採用します。高速化率は旧時間 / 新時間で、1 より大きいほど高速です。個別時間の中央値の比とは区別します。

汎用 `-O2 -DNDEBUG` と、これに `-march=native -ftrivial-auto-var-init=zero` を追加した条件を測定します。両条件とも `-std=c++23` を使います。ライブラリ内の既存の GCC O3 指定は旧・新で共通です。生の各試行、CPU・コンパイラ情報、ハッシュは指定した出力先に保存し、生成ログはコミットしません。

## 検証範囲

永続 unit test には長さ 257・511・1024 limb と、短い側 8・9・16・32・33 limb の組合せを追加しました。独立した基数 10^4 の筆算、交換した入力、符号、全桁 9 の最大繰り上がりを確認します。

2026-10-17 の改訂版では、GCC 14.2 の assertion 有効の bigint・bigint_input・fast_io unit test と、BigInt の ASan・UBSan が通りました。クラウド環境の ptrace 制約により LeakSanitizer は無効化しています。さらに Python 整数を独立した正解として、856 ケースについて入力順の交換・複合代入を含む 4 形式と自己別名の自乗を確認しました。長い側 255・256・257・258・511・1024 limb、短い側 8・9・16・31・32・33・34 limb、全桁 9・ランダム・疎・途中と末尾のゼロ・4 通りの符号、および 10000 limb の最大係数を含みます。ローカルには Clang と Mac がなく、それらの成功は CI で別途確認します。

## 採用前の実験

筆算の呼び出し箇所を後段にもう一つ追加した初版も、全 30 セル・210 組を最後まで測定しました。対象セルでは汎用 4.86～14.37 倍、native 5.20～13.99 倍でしたが、変更対象外の 32×32 limb が汎用で 0.905 倍、257×33 limb が 0.970 倍でした。32×32 の個別中央値は旧 2.08 µs、新 2.38 µs です。native の同じ 2 セルは 1.028 倍、1.010 倍でした。

この初版では GCC が候補側の筆算を out-of-line にし、比較元では inline にしていることを確認しました。因果関係を断定せず、条件を既存の一つの呼び出し箇所へまとめた同値な改訂版を別の実装として再検証しました。初版の不利な値は除外せず残し、改訂版は小さい対照だけでなく全条件を測定しました。初版の実測最短バッチは 0.200005736 秒でした。

## 事前に限定した対照の追加確認

実装・ソース・バイナリを変更せず、上記の対照 5 種を両条件で各 21 組だけ追加測定しました。実測 0.20 秒以上という条件と交互順序は同じです。この一度で終了し、有利になるまで再測定していません。下表の「追加」は 21 組、「統合」は改訂版の当初 7 組と追加 21 組の全 28 組です。異なる実装の初版は統合していません。

| generic | 257 × 33 | 0.977 | 0.982 | 58.463 | 58.592 | 0.998 |
| generic | 32 × 32 | 1.008 | 1.028 | 1.667 | 1.651 | 1.010 |
| generic | 256 × 16 | 0.991 | 0.992 | 10.268 | 10.266 | 1.000 |
| generic | 1024 × 1024 | 1.044 | 1.022 | 644.053 | 629.516 | 1.023 |

| native | 257 × 33 | 0.976 | 0.978 | 60.674 | 61.778 | 0.982 |
| native | 32 × 32 | 0.999 | 0.993 | 1.692 | 1.758 | 0.962 |

native の 32×32 は追加の対ごとの比で 0.999 倍、統合で 0.993 倍でした。ただし統合した個別中央値の比は 0.962 倍で、約 0.067 µs の差が残ります。native の 257×33 は統合の対ごとの比が 0.978 倍、個別中央値が 60.674→61.778 µs です。したがって「全入力で悪化しない」とは主張しません。対象の不均衡乗算の 5.14～14.95 倍と、対照で残る小さい差・大きな測定変動を併記します。AtCoder 実機や Mac の速度は測定していません。

この確認は通常の再現スクリプトで作成した同じ `generic` / `native` バイナリに、対照の二つの limb 数と試行数 `21` を渡して実行できます。生成された各試行と初版・改訂版・追加確認の全記録は外部の出力先に残し、リポジトリへ生成ログは追加しません。

# Dynamic Wavelet Matrix の追加検討

2026-10-20～21。比較元は `50125422751b58e79a3550b66a9261efedf4cf03`。
[ABC343 F](https://atcoder.jp/contests/abc343/tasks/abc343_f) に対して提供された新しい Nim 実装を参考に、葉の配置、構築、更新を再検討する。
この資料の候補比較は最終実装の測定と分けて記録する。
採用構成は容量8192・下限1/4・高さの境界だけ葉数を減らす構築・左右同時下降・葉内 select の二分探索。
最終構成を凍結し、比較元・Nim と同じ入力で測定した。

## 参照実装

新しい添付は [kemuniku/cplib の `244c855f`](https://github.com/kemuniku/cplib/tree/244c855f5961a2ce03a3acebed8eac1f5f4099fc) を展開したソースで、ライセンスは [CC0-1.0](https://github.com/kemuniku/cplib/blob/244c855f5961a2ce03a3acebed8eac1f5f4099fc/LICENSE)。
原文には未使用の `originalSource()` テンプレートも含まれる。
原文 SHA256 は `88fdb69f361231db7a7cdf6721454f28e60686ba66945e9a652d64bfa84d29f5`。
原文を変更せずキャッシュに保存し、依存8ファイルと LICENSE を固定コミットから取得して、それぞれの SHA256 を記録した。
API 計時版では依存部分を維持し、末尾の main だけを、操作列の読み込みと回答領域確保を計測前に行う main に置き換えた。
[参照記録](results/dynamic_wavelet_nim_round2/nim-reference.json) に原文・計時版・コンパイラ・生成された backend コマンド・バイナリのハッシュがある。

前回の [4分実装の比較](dynamic_wavelet_quaternary.md) は別の CPU・GCC と旧 Nim コミットを使用しているため、今回の時間との直接比較には使わない。

Library Checker [Point Set Range Frequency](https://judge.yosupo.jp/problem/point_set_range_frequency) の時間順 AC も再調査した。
[393918](https://judge.yosupo.jp/submission/393918) と [312395](https://judge.yosupo.jp/submission/312395) は取得時点でともに34 ms。
両者とも全クエリを先読みし、値ごとに代入・区間頻度のイベントをまとめ、bitset を持つ Fenwick Tree で処理している。
この問題では有効だが、任意位置への挿入・削除、順位、直前値を持つオンライン Wavelet Matrix の代替にはならない。
今回はこのオフライン化を公開 API に取り入れない。
提出 URL・取得日時・原文 SHA256 は [Library Checker 参照記録](results/dynamic_wavelet_nim_round2/lc_reference.json) にある。
judge の34 msとローカルの下表は測定環境・処理内容が異なる。

## 実装上の違い

| 項目 | 比較元 C++ | 新しい添付 Nim | 検討した C++ 候補 |
| --- | --- | --- | --- |
| 段と内部木 | 4分、32分木 | 4分、32分木 | 既存を維持 |
| 葉の上限 | 1024要素 | `FastQuadVector` は8192要素 | 1024、4096、8192、16384を比較 |
| 葉の統合・再配分の下限 | 容量の1/2 | 容量の1/4 | 1/2と1/4を比較 |
| 初期構築の目標 | 容量の3/4 | 葉数を容量から決め、均等に詰める | 容量まで詰める構築と比較 |
| 葉の2 bit列 | low/high の別配列 | low/high の別配列 | 維持 |
| 葉の累積個数 | 64要素ごとに4種類の16 bit個数 | Fast設定も64要素ごと | 4種類を64 bitとしてまとめて差分を加算 |
| 葉の挿入・削除 | word を順にずらす | SIMD で桁の移動と累積個数更新 | AVX2 の4 word処理と scalar を比較 |
| 葉内の値変更 | 変更前後2種類の累積個数を順に更新 | 4種類をまとめた差分を更新 | 64 bit差分を SIMD で複数wordに反映 |
| 更新時の順位 | 下降中に4種類を蓄積 | 変更した桁に必要な順位を返す | 葉で旧桁を得てから必要な1～2種類だけを加算 |
| 内部木の個数更新 | 旧桁・新桁を別に更新 | 必要な旧桁・新桁を更新 | 同一のループで旧桁・新桁を更新 |
| 段ごとの offset 更新 | 旧桁の後を減算し、新桁の後を加算 | 旧桁・新桁に応じた更新 | 相殺される部分を更新せず、旧桁と新桁の間だけ変更 |

8192に大きくするだけでは葉内の移動が増える。累積個数をまとめた差分と SIMD による移動を組み合わせて比較する。
16 bit個数は葉内だけに使い、内部木の部分木サイズ・個数は従来の32 bitのまま。
64 bit差分は有効な個数の増減として計算し、桁をまたぐ借り・繰り上がりが残らない条件で使用する。
scalar の実装も残す。

容量まで詰めると葉数が減る一方、更新で早く分割される可能性がある。
例えば20万要素・容量8192では、容量の3/4を目標にすると33葉、容量から葉数を決めると25葉となり、32分木の段数も変わる。
この境界の効果が大きいため、20万要素の結果だけで一般的な速度を判断しない。
葉サイズ・木の段数の境界を含む別サイズと、更新の多い入力も検証対象とする。

## コンパイルと測定条件

Linux x86_64、WSL2、Intel Core i7-13700F、CPU2固定、GCC15.2.0。
Nim は公式配布の2.2.4で、配布元の SHA256 と照合した。
Nim の C/C++ backend も C++ 比較と同じ GCC15.2 のインストールを使用する。
この CPU は AVX2 に対応し、AVX-512には対応しない。
添付が要求する AVX-512 kernel の分岐はこの環境では選択されない。
AVX-512経路の速度は未測定。

C++ は `-std=gnu++23 -O2 -march=native -ftrivial-auto-var-init=zero -UNDEBUG -fno-lto`。
既存のヘッダー内 O3 指定は維持する。全条件で FastInput/FastOutput と公開 `kth_largest(0)`、`prev_value`、`count` を使う。
主比較は既定の符号付き32 bitを維持し、最終比較では Nim に合わせた符号なし30 bitも別に測る。

Nim の `optimize()` は通常の AtCoder コンパイルの後、別の指定で自分を再コンパイルする。
この差を隠さず、次の4条件を分けて保存する。

| 条件 | main | コンパイル |
| --- | --- | --- |
| `official_stream` | 提供されたオンライン処理 | AtCoder 公開 Nim C++ backend・release指定 |
| `official_api` | 入力と回答出力を計測外へ移した処理 | 上と同じ |
| `optimized_stream` | 提供されたオンライン処理 | 提供 `optimize()` の第2段と同じ C backend・danger・ARC・LTO・native指定 |
| `optimized_api` | 入力と回答出力を計測外へ移した処理 | 上と同じ |

`official_*` は [AtCoder 公開指定](https://img.atcoder.jp/file/language-update/2025-10/language-list.html) の
`nim cpp -d:release --opt:speed --multimethods:on` などを使い、`-d:second_compile` で自己再コンパイルの呼び出しだけを抑止する。
Nim 標準設定から生成される backend は C++17・O3で、C++側のO2と同一指定ではない。
Fast設定の依存内部には、元から bounds/field checks を省く trusted 経路もある。
依存全体の checks を追加で無効にはしない。

`optimized_*` は `nim c -d:danger -d:second_compile -d:useMalloc --gc:arc --panics:on --opt:speed --checks:off` と、
`--passC:"-flto -m64 -march=native -ffast-math -funroll-loops -fipa-pta" --passL:"-flto"` を使用する。
backend 言語・チェック・最適化指定が違うため、公式指定の結果とは別条件として扱う。
全 Nim 条件は提供通り符号なし30 bit・`FastQuadVector` であり、公開操作の呼び出しも同じ。
ソース内の `-mavx2` 指定も維持する。
入出力も各ライブラリの実装をそのまま使うため、通常ファイルに対して C++ の FastInput は mmap、
提供 Nim は既定で mmap を無効にした読み込みとなる。
オンライン main の全体時間にはこの差も含まれ、API 処理時間では入力・出力を除く。

コンパイル・テスト・計測は共通の `/tmp/cp-wm-opt.lock` を排他取得し、重ねて実行しない。
計時は blocking wait、通常ファイルの標準入力・標準出力、1回のウォームアップ後に実行順を混ぜる。
全ての出力を独立 oracle の正答 SHA256 と照合する。
API 時間では、操作列の読み込み・保存・回答領域の確保は計測前、回答出力は計測後。
構築と操作の process CPU・wall、およびプロセス全体の CPU・wall は区別して記録する。

## 入力

大入力はいずれも $$N=Q=200000$$。値は1～10億。
独立した top-two segment tree を oracle とし、入力・回答 SHA256 と操作内訳を manifest に保存する。

| 入力 | 内容 |
| --- | --- |
| random30 | ランダムな値・位置・区間、10万回ずつの代入と検索 |
| duplicates16 | 値が1～16、10万回ずつの代入と検索 |
| uniform_same | 初期値・代入とも全て7 |
| no_op_random | 値は広い範囲、代入は現在と同じ値 |
| clustered | 更新位置の90%が中央、残りはその近傍 |
| short | 検索の半分が長さ1、残りは長さ2～16 |
| update_heavy | 198000回の代入、2000回の検索 |
| query_only | 20万回の検索、代入なし |

乱数種は既存6種が20261020～20261025、追加2種は20261027・20261028。
小入力4種の18294回答では、segment tree oracle 自体を Counter とソートで照合した。
新しい小入力には、32770要素と、4096・8192・16384・32768付近の位置を含めた。

## 候補の選別

[screen1](results/dynamic_wavelet_nim_round2/screen1.json) は1回の選別。
8192の大きい葉・容量の1/4を下限とする再配分・密な初期構築・SIMD更新を組み合わせた `full8192` で、
random30 の操作時間が328.458 msから275.849 ms、query_only が263.041 msから162.129 msとなった。
葉を大きくしただけの `block8192` は random30 が344.505 ms、update_heavy が399.493 msで、比較元より遅かった。
`full8192` も update_heavy は366.610 msから368.276 msへ増えた。
この1回の結果を最終結果には使わない。

[screen2](results/dynamic_wavelet_nim_round2/screen2.json) は1回のウォームアップと3回の測定。
大きい葉の移動を従来の処理に戻した `legacy_full8192`、差分をまとめても SIMD を使わない `packed_full8192`、
区間の左右を同時に下降する `pair_full8192`、下限を1/2にした `half_full8192`、容量16384も比較した。

| 候補 | random30 操作 ms | update_heavy 操作 ms | query_only 操作 ms |
| --- | ---: | ---: | ---: |
| 比較元 | 336.615 | 366.292 | 263.220 |
| full8192 | 279.207 | 372.209 | 160.371 |
| 従来の葉移動・full8192 | 350.088 | 513.092 | 160.207 |
| 差分更新のみ・SIMDなし | 340.706 | 488.563 | 159.568 |
| 左右同時下降・full8192 | 277.411 | 367.880 | 157.802 |
| 下限1/2・full8192 | 280.428 | 368.886 | 160.556 |
| full16384 | 331.575 | 471.695 | 165.732 |

この比較では、大きい葉の更新に SIMD を組み合わせる必要があった。
下限1/4と1/2の差や左右同時下降の効果は小さいため、さらに別サイズ・更新内訳を確認して決める。

[screen3](results/dynamic_wavelet_nim_round2/screen3.json) は3回の測定で、
葉内更新を改善した上で、必要な順位だけを集計する変更、内部木の個数更新をまとめる変更を順に加えて比較した。
`full8192` という候補名は共通だが、各記録のソースハッシュで版を区別する。

| 候補 | random30 操作 ms | update_heavy 操作 ms | short 操作 ms |
| --- | ---: | ---: | ---: |
| 比較元 | 328.900 | 372.605 | 311.879 |
| 葉内更新を改善 | 277.329 | 372.938 | 264.052 |
| 葉内更新＋必要な順位だけ集計 | 281.614 | 373.358 | 264.447 |
| 上記に内部木の個数更新の融合も追加 | 267.054 | 355.825 | 253.172 |
| 上記に左右同時下降も追加 | 267.954 | 356.526 | 254.324 |

葉内更新だけの候補を基準に、順位の集計だけを加えると速くならない入力もあったが、
内部木の個数更新もまとめた構成では更新の多い入力まで改善した。
左右同時下降は検索中心では少し改善する一方、混合入力では追加の利益が見えない場合もあり、必須とはしない。

追加の [サイズ境界の比較](results/dynamic_wavelet_nim_round2/screen_sizes.json) は、
8192・32768・131072・196608要素、それぞれ10万操作の random30 と short を3回ずつ測った。
196608要素は容量8192の24葉へちょうど詰まるため、
初期の代入で葉分割が続き、32葉を超えて内部木が一段深くなる場合があった。
容量の3/4を目標にする構築と比べ、random30 は129.323 msに対して160.800 ms、
short は119.720 msに対して151.414 msとなり、密な構築が約24～26%遅かった。
20万要素での大きな改善だけを根拠に、全ての初期葉を容量まで詰める案は採用しない。

そのため、通常は容量の3/4を目標にし、それによる葉数が32の累乗を超えて余分な段を作り、
かつ容量を超えずその累乗の葉数へ収められる場合だけ、葉数を減らす候補を追加した。
例えば20万要素では、33葉を32葉へ減らし、各葉を6250要素とする。
25葉にほぼ満杯まで詰める場合と比べ、木の高さを抑えたまま更新用の空きを残せる。
この構築を採用し、別サイズと各公開操作でも確認する。

## 公開操作の補助比較

[操作別の記録](results/dynamic_wavelet_nim_round2/api_screen.json) は、
符号付き64 bit・符号なし64 bit・符号付き31 bit・符号なし7 bitについて、
access、代入、同値代入、挿入、削除、count、rank、select、kth、1境界・2境界の頻度、prev、next を比較した。
これは容量8192・下限1/4・密な初期構築・左右同時下降の候補で、最終の境界だけ葉数を減らす構築とは異なる。
小入力は1100要素・1400操作、大入力は10万要素・2万操作、3回の測定。
小入力104通りを独立した vector oracle と照合し、大入力312回は全回答と最終配列を比較した。

符号なし7 bitの select は2.69 msから4.03 msへ遅くなった。
葉を大きくしたことで、選択対象の word を順に探すコストが増えたため、

## 最終比較

採用構成について、同じ公開 API・同じ呼び出しの符号付き32 bit版と、Nim に値域を合わせた符号なし30 bit版を別に測定した。
オンラインで読みながら処理する全体時間と、入力を除いた API 時間を分け、7回の中央値を記録した。

以下は [最終記録](results/dynamic_wavelet_nim_round2/final.json) の7回の中央値。単位は ms。
C++8条件・Nim4条件について、大入力の672回の測定と96回のウォームアップ、および小入力48通りの全回答が一致した。
構築・入出力を含むオンライン処理の wall 時間は次の通り。

| 入力 | 比較元 C++・32 bit | 最終 C++・32 bit | Nim 公開指定 | Nim optimize 指定 |
| --- | ---: | ---: | ---: | ---: |
| random30 | 372.682 | 289.771 | 357.780 | 326.316 |
| duplicates16 | 89.390 | 69.202 | 87.999 | 79.898 |
| uniform_same | 25.038 | 23.124 | 30.068 | 23.424 |
| no_op_random | 221.463 | 142.499 | 183.558 | 157.183 |
| clustered | 360.372 | 280.413 | 354.503 | 322.010 |
| short | 349.899 | 280.463 | 314.817 | 304.380 |
| update_heavy | 406.869 | 361.767 | 423.076 | 424.840 |
| query_only | 302.663 | 191.964 | 242.676 | 192.989 |

既定の型と公開 API を維持した比較で、全体時間は約8～37%短縮した。
乱数値を代入する通常の混合入力は約20～22%、更新99%でも約11%短縮した。
Nim optimize 指定との query_only と uniform_same の差は小さく、これらの差だけから優位性を主張しない。
全体時間には上記の入出力実装の違いも含まれる。

## 最終構成の検証

[検証記録](results/dynamic_wavelet_nim_round2/validation.json) と [ログ](results/dynamic_wavelet_nim_round2/validation.log) に150コマンドを保存し、全て終了コード0だった。

- GCC・Clangで関連3ヘッダーと6単体テストを確認。
- 主要3テストを ASan+UBSan と scalar 経路でも確認。
- Library Checker の公式49ケースを GCC・Clangで実行し、計98回・8889012トークンが正答と一致。
- ドキュメント180件の metadata と、関連3件の展開済みコードのコンパイルを確認。

検証したヘッダーの SHA256 は最終比較の凍結ソースと一致する。
AVX-512経路はこの CPU では実行していない。
[測定 helper の確認](results/dynamic_wavelet_nim_round2/harness_check.json) では、全 Python の構文、
採用設定を再適用しても変わらないこと、候補パッチから再構築した全ヘッダーが screen3 の記録と一致することも確認した。

## 再現

[専用ディレクトリ](dynamic_wavelet_nim_round2/README.md) に生成・ビルド・検証・比較スクリプトがある。
元の添付は `prepare.py --source` に渡し、原文の SHA256 が上記と同じことを確認する。
Nim のツールチェーンを指定しなければ、公式2.2.4配布を取得して公開 SHA256 と照合する。

```sh
python3 test/benchmark/dynamic_wavelet_nim_round2/cases.py \
  --root .verify-helper/cache/dynamic-wavelet-nim-round2 --small --large
python3 test/benchmark/dynamic_wavelet_nim_round2/prepare.py \
  --source /path/to/supplied.txt \
  --work .verify-helper/cache/dynamic-wavelet-nim-round2/reference --compile
python3 test/benchmark/dynamic_wavelet_nim_round2/export_reference.py \
  --reference .verify-helper/cache/dynamic-wavelet-nim-round2/reference \
  --output /path/to/nim-reference.json
```

`compare.py prepare` は比較元コミットと作業中のヘッダー5件・ドライバを凍結してビルドする。
`compare.py measure` は凍結した C++8条件と Nim4条件を測り、全回答の SHA256 を確認する。
指定コマンドは専用ディレクトリの README にある。
既存の測定記録は上書きせず、新しい出力先を使う。

# FPS の対数

比較元は `7fb5f2897349aa0a11c18e3ab56f3e4815319017`。2026-10-18 UTC に測定した。公開 FPS API を維持する。

## 上位提出との比較

[409452](https://judge.yosupo.jp/submission/409452)・[409363](https://judge.yosupo.jp/submission/409363)・[409264](https://judge.yosupo.jp/submission/409264) の対数を確認した。今回再取得した順位・時刻・ソース SHA-256 は [参照一覧](results/fps_log_reference.json) にある。掲載時間はそれぞれ 13・14・15 ms だった。最終測定は上位 2 提出のソースを変更せず、同じ入力・コンパイラ・フラグで比較する。

409452 は最大 4 ブロックの対数微分、次数 8 の環を葉とする部分変換、必要な半分だけの逆変換、2 × 2 Toeplitz 積、32 要素の並列な逆数計算を利用する。既存の対数は、32 ブロックの汎用級数除算を呼び、出力全体の整数逆元表を別に作っていた。

## 変更

半分だけを復元する逆変換も比較したが、21 試行の再比較では両半分の版が短かったため、最終版は両半分を復元し、必要な半分だけを使う。

出力次数を `d` とし、`k` を `(d-1)/4` 以上の最小の 2 冪として、`f'/f mod x^(d-1)` を最大 4 ブロックで求める。初めに `h=1/f mod x^k` と隣接する入力の窓 `W_s=f[(s-1)k,(s+1)k)` を変換する。ブロック `j` は、既知のブロックとの積和の上半分を微分から引き、`h` を掛けた積の下半分で求める。

4 ブロックの場合は `W2*(q0+q1)`・`(W1-W2)*q1`・`(W3-W2)*q0` の 3 積で、`W2*q0+W1*q1` と `W3*q0+W2*q1` を計算する。後者を窓 `W3` の領域へ保存し、続くブロックで使う。`q1` と `q2` は同じ作業領域を再利用する。

積分はブロックごとに行う。4 本の SIMD 列で整数の累積積を求め、逆向きに逆元を復元しながら係数を割る。逆数表全体を保持せず、未使用の作業領域の後半を累積積に使う。最後の 32 要素未満は有効な添字だけを読み書きし、入力と出力に余分な要素を要求しない。

内部部品は `components/fps_log.hpp` に分離した。x86 / AVX2、256 項以上、入力が 64 項以上の経路で使う。変換長が既存 NTT の上限を超える場合も汎用経路へ戻す。Mac の ARM などでは従来の級数除算を使う。Clang がラムダへ外側の関数の AVX2 指定を引き継がないため、各 SIMD ラムダにも `target("avx2")` を明示する。冪も対数微分の改善を利用するが、積分は行わない。

## 測定条件

Linux x86_64、AMD EPYC 9V74、GCC 14.2.0、CPU 2。`-std=c++23 -O2 -DEVAL -DONLINE_JUDGE -ftrivial-auto-var-init=zero -march=haswell`、assert 有効。THP の設定、ソース・入力・ドライバーの SHA-256、公式問題のコミット、全試行を JSON に保存する。

予備実行 1 回の後、seed 20261018 で順番をシャッフルして 9 回測定する。各試行は新しいプロセスとする。計算部分は入力生成とチェックサムを除き、確保・初期化を含む。全版のチェックサムを照合する。プロセス全体は通常ファイルから読み、通常ファイルへ出力する。全出力を公式 checker で検証する。測定中にコンパイルや検証を並行実行しない。

Library Checker 実機での掲載時間とローカル時間は混ぜない。最速の獲得はローカル測定だけでは確認できない。

## 候補

追記: 最速版をそのまま使う比較、API 境界、入出力、処理別の差は [追加診断](fps_log_gap.md) にまとめた。下記の予備実装で改善がなかったことは、最速版の専用バックエンド全体を再現できないことを意味しない。

`--log-candidates` で、積分を独立した逆数表へ戻す版、Toeplitz の共有を外す版、逆変換の片半分だけを復元する版、2・8 ブロックの版を同じ条件で比較する。完全 NTT、葉ごとの積と変換の融合、256・2048・8192・32768 ワードの再帰的な分割も予備測定したが、採用版を上回る改善を確認できず採用しなかった。

## 検証

影響する 19 ヘッダーと 14 単体テストを GCC で確認し、同じ 14 単体テストの ASan・UBSan も成功した。逆変換の採用版への切り替え後は、対数と汎用係数型を含む 2 単体テストを通常設定・ASan・UBSan で再確認した。

新しいテストは、3・4 ブロックの切り替わり、2 冪の前後、入力が出力次数より短い場合と長い場合、剰余上限付近の内部値、汎用係数型を確認する。対数は素朴な漸化式、および微分した対数と元の多項式との積で照合する。入力配列の内部値が保存されること、半分の逆変換と Toeplitz 積の別計算との一致、整数逆数の 32 要素境界、末尾ちょうどの配列と作業領域の番兵も確認する。

アルゴリズム版で公式の 22 ドライバー・596 ケースが成功した。AVX2 指定の追記後は、対数・冪の 2 ドライバー・62 ケースも再確認した。yukicoder 1307 の 2 ドライバーはローカルにトークンがないため CI で確認する。Clang と macOS も CI で確認する。ローカルの LeakSanitizer は既存環境の ptrace 制約のため無効にし、`ASAN_OPTIONS=detect_leaks=0` と `UBSAN_OPTIONS=halt_on_error=1` を指定した。

127 ヘッダーの文書を確認し、影響する 19 結合ヘッダーをコンパイルした。ローカルの文書生成には利用可能な GCC を使った。

記録は [選択範囲](results/fps_log_selection.json)、[通常](results/fps_log_check.log)、[追加テストの最終確認](results/fps_log_final_check.log)、[Sanitizer](results/fps_log_sanitize.log)、[最終 Sanitizer](results/fps_log_final_sanitize.log)、[公式ケース](results/fps_log_judge.json)、[AVX2 指定後](results/fps_log_final_judge.json)、[文書](results/fps_log_docs.log) にある。

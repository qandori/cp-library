# Dynamic Wavelet Matrix のベンチマーク

2026-10-16、macOS arm64 / GCC 15.2、`-std=c++23 -O2 -DNDEBUG`。初期要素数・操作数ともに 100,000、値の bit 数は 20、seed 713、実行順を変えた 3 回の中央値です。単位は ms、すべての候補で checksum が一致しています。

```sh
g++ -std=c++23 -O2 -DNDEBUG -I . test/benchmark/dynamic_wavelet_matrix.cpp -o /tmp/dwm-benchmark
/tmp/dwm-benchmark library mixed 100000 100000
/tmp/dwm-benchmark treap mixed 100000 100000
```

引数は実装、入力の種類、初期要素数、操作数です。入力生成と最終確認は計測に含めません。以下は構築を除いた操作時間です。

| 入力 | 1 bit / ノードの Treap | 512 bit・8 分岐 | 両端の順位を別々に計算 | 代入を削除＋挿入で処理 | 採用実装 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `mixed`：6 種類の操作 | 2183.16 | 141.13 | 140.00 | 137.91 | 134.22 |
| `updates`：代入のみ | 4249.40 | 275.46 | 273.56 | 268.04 | 282.95 |
| `queries`：問い合わせのみ | 1453.80 | 95.42 | 69.87 | 75.67 | 75.39 |
| `duplicates`：16 種類の値 | 1292.38 | 49.10 | 50.26 | 70.09 | 52.17 |
| `front`：先頭で変更 | 1590.45 | 133.35 | 126.47 | 119.95 | 130.52 |
| `short`：区間長 16 以下 | 674.46 | 41.23 | 33.39 | 31.47 | 31.62 |
| `append`：末尾で変更 | 1509.95 | 124.68 | 115.94 | 112.41 | 114.45 |

`mixed` の構築は Treap 45.02 ms、採用実装 7.71 ms、操作後の確保済みノード領域はそれぞれ 96,000,960 byte と 504,160 byte でした。Treap は 1 bit を 24 byte のノードで管理し、挿入時の領域拡張で容量が増えます。採用実装は bit を詰めたブロックを B+ 木で管理し、添字による参照、ノードの再利用、一括構築を使います。

最初に 128・256・512・1024 bit のブロックと、4・8・16・32 分岐を比較しました。ブロック内の順位を毎回数える段階では 512 bit が更新に有利でしたが、各 64 bit word の前にある 1 の個数を 16 bit で保持する構成にすると、1024 bit の検索性能とメモリ使用量が有利になりました。累積カウンタは bit のシフトと同じループで更新し、更新ごとの全再計算を避けています。

512 bit での累積カウンタの比較は 5 回の中央値で、混合操作 153.02 → 146.57 ms、問い合わせ 116.66 → 97.68 ms、代入 276.10 → 263.76 ms、短い区間 56.11 → 44.19 ms でした。ブロックの前半だけの個数を持つ案も試しましたが、混合操作 150.33 → 155.63 ms、問い合わせ 110.94 → 111.85 ms となり採用していません。

代入では位置が一致する段を直接更新し、全要素で同じ bit の段は変更を省略します。全域ランダムの代入だけなら削除＋挿入が少し速い一方、重複が多い入力では直接更新が有利でした。順位検索は共通経路を共有し、右端の子の探索を左端の子から始めます。独立した順位検索が速い入力もありますが、混合操作と短い区間を含めて共有する構成を選びました。

実装名は `library`・`treap`・`separate`・`erase_insert`、ブロックと分岐数の候補は `128x4`・`128x8`・`256x4`・`256x8`・`256x16`・`512x4`・`512x8`・`512x16`・`512x32`・`1024x8`・`1024x16` です。`mixed` は挿入・削除・代入・区間順位・値未満の個数・一致する値の個数を同じ確率で実行します。
